# PROMPT — INTEGRACIÓN DE IMPORTACIÓN DE FUERZAS PARA PILAS DESDE FRAMES/JOINTS Y PIERS/SHELLS EN ARCO

Estoy desarrollando **ARCO**, una aplicación de escritorio en **Visual Basic .NET** para análisis y diseño estructural.

Actualmente ARCO ya tiene un **módulo de Pilas completamente funcional**, con lógica de cálculo, diseño, formularios, almacenamiento de información y una metodología existente para importar ciertos datos de cimentación.

## OBJETIVO PRINCIPAL

Necesito ampliar el módulo de Pilas para que pueda reconocer e importar automáticamente las demandas provenientes de un modelo de ETABS bajo **dos situaciones estructurales diferentes**:

1. **Columnas modeladas como Frame**, cuya cimentación llega a un Joint.
2. **Columnas, muros o elementos modelados como Shell**, agrupados mediante un **Pier**, cuyas demandas deben obtenerse a partir de las fuerzas en la base del Pier.

La modificación debe ser estrictamente una **mejora incremental del módulo actual**.

### REGLA FUNDAMENTAL

**NO eliminar, reemplazar ni romper ninguna funcionalidad actual del módulo de Pilas.**

Todo lo que hoy funciona debe continuar funcionando.

La nueva funcionalidad debe incorporarse como:

> **una nueva opción/fuente para importar fuerzas de diseño de las pilas.**

No quiero reconstruir el módulo de Pilas desde cero.

# 3. DOS TIPOS DE ELEMENTOS QUE PUEDEN ALIMENTAR UNA PILA

La nueva arquitectura debe soportar al menos estos dos casos.

## CASO A — COLUMNA MODELADA COMO FRAME

Conceptualmente:

```text
FRAME / COLUMNA
       ↓
     JOINT
       ↓
   CIMENTACIÓN
       ↓
      PILA
```

Para estos elementos, necesitamos detectar automáticamente cuál es el Joint inferior correspondiente al elemento Frame.

Luego debemos buscar sus demandas/reacciones en las tablas de ETABS.

La relación sería:

```text
Frame
  ↓
Joint inferior
  ↓
Joint Reaction
  ↓
Fuerzas para diseño de la pila
```

---

# 4. DETECCIÓN DEL JOINT INFERIOR DE UN FRAME

No asumir que el Joint I o J siempre corresponde a la base.

Utilizar las coordenadas y elevaciones.

Para cada Frame vertical:

```text
Joint I → Xi, Yi, Zi
Joint J → Xj, Yj, Zj
```

El Joint de menor elevación debe identificarse como el extremo inferior, dentro de las tolerancias correspondientes.

Por ejemplo:

```text
Zbase = Min(Zi, Zj)
```

La lógica debe funcionar aunque ETABS haya definido el Frame en dirección ascendente o descendente.

---

# 5. COLUMNAS FRAME QUE REALMENTE CORRESPONDEN A PILAS

No debemos asumir que todo Frame vertical del modelo genera automáticamente una pila.

Debemos limitar la búsqueda al nivel de cimentación o al nivel que corresponda según la estructura actual de ARCO.

Analiza cómo ARCO identifica actualmente:

* columnas;
* apoyos;
* cimentaciones;
* Story inferior;
* elementos asociados al módulo de Pilas.

Utiliza esta información como primer filtro.

Posteriormente podemos proporcionar al usuario una lista de candidatos.

# 7. CASO B — ELEMENTO MODELADO COMO SHELL / PIER

También tenemos columnas o muros modelados mediante elementos Shell.

Estos Shells pueden estar agrupados en ETABS mediante una etiqueta:

```text
PIER
```

Conceptualmente:

```text
SHELLS
   ↓
PIER
   ↓
Pier Forces - Bottom
   ↓
CIMENTACIÓN
   ↓
PILA
```

Para estos elementos **NO quiero tomar cada Joint inferior del Shell como una pila diferente**.

Un Pier puede tener múltiples nodos en su base debido a la discretización del Shell.

La unidad estructural debe ser el **Pier completo**.

---

# 8. FUERZAS DE DISEÑO DEL PIER

Para los elementos Shell/Pier, las fuerzas principales para diseño deben provenir de:

> **Pier Forces en la base del Pier**

Es decir, utilizar la fila correspondiente a:

```text
Pier
Story
Load Case / Combo
Location = Bottom
```

y obtener las seis componentes disponibles, típicamente:

```text
P
V2
V3
T
M2
M3
```

Debes verificar los encabezados y convenciones reales del Excel que te voy a entregar.

No asumir nombres exactos sin revisar el archivo.

---

# 9. NO UTILIZAR LOS JOINTS DEL SHELL COMO PILAS INDEPENDIENTES

Este punto es crítico.

Si un Pier tiene una base discretizada así:

```text
●────●────●────●────●
       PIER P1
```

NO significa que existan cuatro pilas.

Son cuatro nodos del modelo numérico pertenecientes a una misma base estructural.

La demanda principal debe corresponder al resultante del Pier.

Conceptualmente:

```text
PIER P1
   ↓
P, Vx, Vy, Mx, My, T
   ↓
PILA
```

---

# 12. JOINT REACTIONS DEL PIER COMO VALIDACIÓN

Para los Piers quiero que las **Pier Forces sean la fuente principal de demandas**.

Sin embargo, si la información disponible lo permite, podemos utilizar los Joint Reactions de los nodos inferiores como herramienta de validación.

Conceptualmente:

```text
FUENTE DE DISEÑO:
Pier Forces - Bottom

FUENTE DE CONTROL:
Joint Reactions integradas
```

No mezclar ambas para generar una única combinación de carga.

La validación puede implementarse posteriormente o dejarse preparada en arquitectura.

4. ARCO analiza las tablas.

5. ARCO reconstruye:
   Stories

   Areas

# 25. PREPARAR LA ARQUITECTURA PARA VARIOS ELEMENTOS SOBRE UNA PILA

Aunque la primera implementación pueda trabajar principalmente 1 a 1, quiero evitar una arquitectura que obligue a:

```text

```

o:

```text

```

Una pila podría posteriormente recibir:

```text
Frame + Frame

Pier + Frame

```

Por lo tanto, conceptualizar:

```text

 ↓
StructuralSupports[]
```

en lugar de:

```text
PILA
 ↓
FrameID
```

Si actualmente la arquitectura no permite esto, no hagas una refactorización destructiva de inmediato.

Propón primero cómo extenderla manteniendo compatibilidad.
